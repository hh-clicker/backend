# HH Clicker Backend

Spring Boot backend локального HH Clicker. Сервис хранит аккаунты, резюме, поиски,
вакансии и историю откликов, координирует Browser Agent и Generation Agent и применяет
миграции PostgreSQL через Liquibase.

## Запуск

Для повседневного запуска всего окружения используйте `infra/compose.yaml`. Отдельный
backend можно запустить из этого каталога:

```powershell
.\gradlew.bat bootRun
```

Требуется PostgreSQL и значения подключения, ожидаемые Spring-конфигурацией.

## Параллельная оценка вакансий

UI запускает оценку сохранённых вакансий через `/api/v1/vacancies/relevance/parallel`.
Backend создаёт отдельный virtual thread на каждую партию до 10 вакансий; число одновременно
выполняемых партий не ограничивается числом процессоров или размером фиксированного пула.
Результаты сохраняются независимо, общий прогресс восстанавливается после обновления страницы.
Фактическое число процессов Codex регулирует Generation Agent по доступной памяти;
сверху действует настраиваемый потолок, по умолчанию 4 одновременные пачки оценки и анализа рынка суммарно;
ожидание ресурса в его очереди не расходует срок выполнения самой партии.
Вызовы к HH и отправка откликов остаются последовательными.

Для контрольного прогона POST принимает `benchmark: true`: оцениваются и уже оценённые
карточки, но ответы не записываются в БД. Подробности контрактов, отмены и срока ожидания —
в [ARCHITECTURE.md](ARCHITECTURE.md).

## Холостой запуск

`POST /api/v1/application-runs` с `mode: "DRY_RUN"` открывает выбранные вакансии только
для сохранения полного текста. Письма не генерируются, отклики не отправляются,
статусы вакансий и очередь не меняются. Максимум 500 вакансий за запуск; случайные
паузы используются как у реальных откликов. Дневной лимит отправок не расходуется.
Результаты доступны в истории запусков; `APPLY` остаётся режимом по умолчанию.

## Срез вакансий для анализа резюме

`/api/v1/market-analyses` создаёт снимок незакрытых вакансий с сохранённым полным текстом для
выбранного резюме. Generation Agent возвращает структурированные JSON-факты трёх видов:
технологии, навыки и домены. Backend проверяет дословные цитаты, сохраняет факты и
сам считает частоты по уникальным вакансиям и компаниям. В обычном отчёте регистр
названия игнорируется, но падежи, сокращения и синонимы не объединяются; название показывается в одном исходном написании в трёх компактных таблицах без цитат
и перечней вакансий. Таблицы отсортированы по весу: первая вакансия компании даёт 1,
каждая следующая — в e раз меньше предыдущей; так массовые публикации одного
работодателя не доминируют над упоминаниями у разных компаний.
Резюме автоматически не оценивается: обычный MD
предназначен для разбора во внешнем чате вместе с актуальным текстом резюме.
Новые анализы выполняют до четырёх партий по 8 вакансий параллельно на virtual threads.
Партии и ID заданий сохраняются в БД (миграция 036), результаты принимаются в любом порядке.
После перезапуска backend продолжает сохранённую работу. Общий лимит Generation Agent для
оценки и анализа — `GENERATION_MAX_CONCURRENT_ANALYSIS=4`; прежняя настройка
`GENERATION_MAX_CONCURRENT_RELEVANCE` работает как fallback. Память может уменьшить допуск.
Старые снимки без записей партий продолжаются прежним путём.
Во время извлечения API после первой завершённой партии возвращает приблизительный
остаток времени: средняя длительность готовых партий по 8 вакансий умножается на
число оставшихся партий. До первого результата оценка не показывается.
Перед стартом `GET /api/v1/market-analyses/preview?resumeId=...&maxVacancies=100&searchId=...&relevanceCategory=TARGET`
показывает, сколько вакансий будет выбрано и дату самого раннего сохранённого текста. Лимит
и фильтры необязательны: без них берутся все вакансии с этим резюме, включая вакансии без оценки. Поиск ограничивает
выборку вакансиями, связанными с ним; совпадающая в нескольких поисках вакансия
в общей выборке считается один раз. `relevanceCategory` принимает `TARGET`, `ADJACENT`,
`UNKNOWN` или `NOISE`; ограничение по последним N применяется после фильтрации.
`POST /api/v1/market-analyses` принимает `resumeId`, необязательные `searchId`,
`relevanceCategory` и положительный `maxVacancies`, фиксирует последние N
вакансий и название поиска в снимке. Для паузы используется `POST .../{id}/stop`:
уже выданные партии завершаются и сохраняются, новые не отправляются. `POST .../{id}/cancel`
окончательно закрывает `RUNNING`, `STOPPING` или `PAUSED` анализ, после чего можно
сразу создать новый. Уже отправленное задание Generation Agent при этом физически
не останавливается, но его результат не применяется; завершённые ранее партии остаются
в истории без готового MD.
Если извлечение остановилось с ошибкой или вручную, `POST /api/v1/market-analyses/{id}/resume`
возобновляет тот же снимок с сохранённой позиции, не запуская повторно готовые партии.
Продолжаются только незавершённые партии; повтор старше семи дней не допускается.
После возобновления оценка времени начинается заново и появляется после следующей
готовой партии, чтобы простой во время ошибки не завышал прогноз.
Завершение и ошибка анализа доступны существующему механизму веб-уведомлений;
в Telegram доступны прогресс и итог анализа при подключённом боте.

`GET /api/v1/market-analyses/{id}/report` скачивает обычный MD. Проверочный вариант
этого же снимка доступен с явным debug-флагом: `GET /api/v1/market-analyses/{id}/report?debug=true`.
В нём сохранены точные, чувствительные к регистру частоты, цитаты с привязкой к вакансиям,
подробная диагностика и полные исходные тексты всех вакансий. В веб-интерфейсе вторая кнопка скачивания
появляется по адресу `/market-analysis?debug=1`. Не пересылайте проверочный MD без
необходимости: он значительно объёмнее обычного. Обычный MD формируется из сохранённого
снимка при скачивании, поэтому существующие завершённые запуски тоже получают таблицы
без повторного анализа вакансий.
Обычный MD также содержит таблицу названий вакансий с частотой, числом компаний и
весом. Одинаковые названия без учёта регистра объединяются, остальные различия
сохраняются; тексты вакансий в обычный отчёт не входят.

## Совместимость обновления

Namespace приложения — `org.hhclicker`. На чистой установке автор миграций — `hh-clicker`.
При обновлении полностью запущенной 1.12.0 авторы двух базовых миграций читаются из истории
Liquibase и подставляются до разбора changelog. Служебные записи не переименовываются,
проверка checksum остаётся включённой. Поддерживаются настроенные схема и имена таблиц истории.

Неоднозначная или отсутствующая базовая история останавливает запуск. Прерванная чистая
установка может продолжиться с непрерывного нейтрального префикса 001–018. Параметры
hhclicker.bootstrap.schemaAuthor и hhclicker.bootstrap.notificationsAuthor зарезервированы
адаптером и не должны задаваться пользователем. Новые миграции добавляются после базовой истории.

Перед обновлением нужна резервная копия БД и проверка её восстановления. Installer сохраняет
данные, но не создаёт дамп и не откатывает миграции. Подробности — в
[архитектуре](ARCHITECTURE.md#persistence-и-миграции).
